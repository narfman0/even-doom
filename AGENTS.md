# even-doom — Agent Reference

AI agents are the primary authors of this codebase. This file captures the architecture, constraints, conventions, and known gaps needed to work on the project effectively.

## Source of truth

- Edit **`.ts` files** only. The `.js` files in `src/` are compiled output — do not edit them.
- Map geometry lives in `src/data/e1m1-data.ts`, generated by `scripts/process-wad.ts` from `doom1.wad`. Do not hand-edit it.
- Sprite data lives in `src/data/sprite-data.ts`, generated by `scripts/process-sprites.ts`.

## Commands

```sh
npm run simulator   # terminal raycaster — fastest feedback loop, no browser needed
npm test            # vitest unit tests
npm run dev         # Vite dev server at localhost:5173
npm run build       # tsc + vite build → dist/
```

Always use `npm run simulator` to verify engine changes before touching the EvenHub layer.

## Architecture

Three layers with a strict dependency direction: `core` ← `even`, `core` ← `simulator`.

### `src/core/` — platform-agnostic engine

**`raycaster.ts`** is the entire game engine:
- Player state: `x`, `y`, `angle` in Doom WAD world units.
- `castRay(angle)` — ray vs. all linedefs via parametric segment intersection. Returns `dist`, `light`, `isTwoSided`, `upperVoidFrac`, `lowerVoidFrac`, `wallNormalDot`.
- `renderAscii(cols, rows)` — casts one ray per column, maps distance to a 70-char density ramp, overlays enemy sprites using Unicode block elements, appends a HUD strip.
- `moveForward(dt)` / `moveBack(dt)` — bare coordinate updates, **no collision detection** (known gap, see below).
- `tick(dt)` — advances enemy AI: move toward player, attack in range.

**`types.ts`** — shared interfaces.

### `src/even/` — EvenHub WebView plugin

- `index.ts` calls `createStartUpPageContainer` once, then runs a 10 fps `setInterval` game loop. Reads `Controls` state each frame.
- `controls.ts` maps IMU x-axis tilt to `turnRate` and ring gestures to timed `moveForward`/`moveBack`/`shoot` pulses.

### `src/simulator/` — Node terminal target

- `index.ts` runs the same 10 fps loop, writes ANSI escape frames to stdout.
- `keyboard.ts` raw-mode stdin; exposes the same state shape as `Controls` so `raycaster.ts` is portable between targets.

## Coordinate system

Doom WAD uses a left-handed coordinate system where north = +Y. This engine's angle convention is standard math (0 = east, increasing counter-clockwise), but the Y axis is **screen-flipped** at the ray cast site:

```ts
const dy = -Math.sin(rayAngle)  // flip: WAD +Y is up, screen +Y is down
```

Enemy positions are also stored in WAD space; the same flip is applied when computing `worldDy` for sprite projection. Keep this in mind when adding any geometry or entity movement.

## Linedef structure

`LINEDEFS` is a flat `Int16Array` with 4 values per linedef: `[v1i, v2i, rightSide, leftSide]`.
- `rightSide` / `leftSide` are indices into `SIDEDEF_SECTORS`.
- `leftSide === 0xFFFF` (`NO_SIDEDEF`) means a one-sided solid wall.
- Two-sided linedefs (both sides present) are portals; they only produce a visible step if floor/ceiling heights differ between sectors.

## EvenHub SDK constraints

| Constraint | Limit |
|---|---|
| Canvas size | 576 × 288 px |
| Text content (upgrade) | Max 2000 chars |
| `createStartUpPageContainer` | Call once only |
| Event capture | Exactly one container may have `isEventCapture=1` |
| IMU pace `P200` | ~200ms between IMU samples |

The ASCII frame at 58×24 is ~1415 chars — keep it under 2000 if changing dimensions.

## Known gaps

- **No collision detection.** `moveForward`/`moveBack` update `x`/`y` directly without checking linedefs. The intersection math in `castRay` is the right primitive to reuse: test the candidate position against all solid linedefs within a radius, then slide along the wall normal if blocked.
- **Enemies walk through walls.** Same root cause — enemy AI in `tick()` moves toward the player with no linedef check.
- **No door/switch logic.** All E1M1 sectors are static; interactive linedefs are ignored.
